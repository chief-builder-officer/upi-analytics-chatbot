1EXECUTIVE SUMMARY

At Mobikwik's pace, leadership asks more UPI questions in a week than any dashboard roadmap could pre-build in a quarter.

A leader types a question; the agent picks the right metric, runs it on a governed semantic layer, and returns a number, a trend, and a "so-what" — without ever touching raw tables. That last clause is the design choice the rest of this document defends.

Most LLM-on-data products fail at the metric layer, not the model layer. They let the model invent definitions for "success rate" or "active user" on the fly, and the answer in chat diverges from the dashboard, the board deck, and the regulator filing. PULSE removes that failure mode by construction: every metric is defined once, owned, versioned. The agent picks one — it doesn't write one. — Why the agent never queries raw tables

3RAW DATA LAYER

A single UPI transaction generates an extraordinary amount of structured signal.

The rails — the four-party model of a UPI transaction (NPCI ↔ PSP ↔ Issuer Bank ↔ Beneficiary Bank), which defines how money moves securely from payer to beneficiary in real time — are designed for traceability and dispute resolution. Every state transition writes a row. This is the data exactly as it lands from production.

Scale problem: at ~10M monthly UPI txns × ~5 state transitions × ~4 raw response payloads, the raw layer alone produces ~200M rows/month EST. Querying this directly is neither cost-effective nor safe — which motivates the semantic layer.

5LIVE LLM AGENT

One LLM, given enough context — not a four-agent contraption.

Because the heavy lifting already lives in the semantic layer, the LLM's job shrinks to one thing: translate natural language into a structured query against a known catalogue. That's a single call to one capable model (GPT-5.5 or Claude Sonnet) with a context bundle of .md files — the metric catalogue, governance rules, schema notes, and a few canonical examples. Multi-step orchestration buys little when the surface area is already constrained; it just adds latency, cost, and failure modes.

The bundle is small (~10–15k tokens), regenerated whenever the metric catalogue changes, and shipped as a versioned artifact. The LLM gets one prompt, returns one structured query, the metric server runs it. End of loop.

Why a single, well-contexted LLM is structurally safer than text-to-SQL

FAILURE MODE WHY VANILLA TEXT-TO-SQL FAILS HOW THE CONTEXT BUNDLE PREVENTS IT
Inventing columns Model hallucinates schema it never saw Catalogue is the only schema the LLM is shown — anything outside it is by definition off-limits.
Wrong joins Model stitches tables based on naming heuristics Metric server owns the joins. The LLM emits a structured metric query, not raw SQL.
Redefining business logic "Success rate" gets reinvented at every query Every definition is in the catalogue, signed off, version-tagged. LLM picks one — never invents.

What PULSE will not do

✕
No raw SQL
If the question doesn't map to a defined metric, it's not answered with invented logic.
✕
No predictions in v1
Forecasting needs its own governance. We earn that surface later.
✕
No write actions
Read-only. No "block this VPA" via chat. Different system, different blast radius.
✕
No PII in answers
PII tokenised at the cleaned layer. PULSE returns aggregates only.
6GOVERNANCE · TRUST · GUARDRAILS

Numbers come from the metric server. The LLM is prompted to quote, not paraphrase.

🔐 Access control

RBAC at the metric level, not the app level. Founder sees everything; a P2P business head sees P2P metrics only. Enforced by the metric server — not the LLM.

🛡️ PII & compliance

All PII tokenised at the cleaned layer. Conversation logs themselves are PII — 90-day retention with right-to-erasure.

💰 Cost & freshness

Every answer carries a freshness timestamp. Per-user daily spend caps; heavy queries auto-routed to a batch tier with "we'll email you" UX.

📜 Audit-grade replay

Every conversation, every quoted number, every compiled query logged with a trace_id. A leader can replay "what did PULSE tell my team last Tuesday?" exactly.

How we know it's working

A 200-question evaluation set runs nightly against a held-out warehouse snapshot, grading the agent on routing correctness, numerical accuracy, and refusal behaviour. GA bar: ≥ 90% accuracy on real questions, ≥ 95% refusal-correct on adversarial probes. Every PR to the agent triggers a smoke-eval before merge — no prompt change ships on vibes.

When the agent isn't sure

An honest "I don't know" beats a confident wrong answer. Three fallback states. None is "answer anyway."

1
WHEN · Ambiguous question or entity
Ask a clarifying question
"HDFC as payer or payee?" — 2–3 disambiguation chips. Healthy rate: 10–20% of questions.
2
WHEN · No governed metric covers the question
Honest "not yet" + ticket
Suggest the closest catalogue metrics; offer a one-click request to the metric stewards.
3
WHEN · System error / access denied
Route to analytics on-call
Pre-fills a Slack / Linear ticket with the question and trace_id. Median resolution < 4 working hours.

9RISKS & MITIGATIONS

Risks I'm watching — and how the design defuses each.

RISKSEVERITYMITIGATION
Leadership trusts a wrong number; bad decision is made HIGH Numerical-drift evals daily; numbers always quoted with metric definition + freshness timestamp.
Catalogue grows slower than questions arrive; users abandon HIGH Dedicated data PM; "request a metric" flow turns gaps into tickets.
LLM costs balloon at scale MED Haiku for routing, Sonnet for narrating; result caching; per-user caps.
RBI / NPCI compliance audit on a quoted number HIGH Every answer carries trace_id, metric version, source query — full replay available.
Internal conflict — "my dashboard says different" MED Make PULSE the source of truth; deprecate conflicting dashboards on a schedule.
